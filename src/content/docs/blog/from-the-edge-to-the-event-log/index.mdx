The feature in this post fits on a sticky note: a signed-in user registers an author, and author names have to be unique within the user's organization.

Shipping it is the short part. The feature then lives for years, and each stage of its life asks something different of the system.

Before any code, someone has to write down what it should do in a form a non-developer can read. On day one you need to know who the user is, which tenant they belong to, where the uniqueness rule lives and whether it holds when two requests arrive in the same second. In month three someone asks to be forgotten, and the author's name is personal data. In month nine a view stops updating and nobody can say why. In year two the event needs a new field, a second service wants to hear about new authors, and an assistant that helps with the code hasn't read your conventions.

Cratis has a piece at each of these points: modeling tools, an edge proxy, an application framework on three server ecosystems, an event store with clients in several languages, a CLI and a browser Workbench for the running system, and a free AI corpus plus MCP servers for assistants. Event sourcing is one strand. Arc doesn't require it, and Chronicle can be used without Arc. Other pieces have their own dependencies and adoption boundaries.

This post follows the author feature through its whole life: model it, start it, build it, protect it, run it, debug it, evolve it, and then walk the same loop with agents doing much of the writing. Each section says what the pieces do, where they stop, and how mature they are. The [ecosystem at a glance](https://blog.cratis.io/the-cratis-ecosystem-at-a-glance/) post is the product list.

Each row is a moment in the feature's life, and nothing here has to be adopted in one go. Maturity varies widely, from released and MIT-licensed to experimental. Each section says which, and [where each piece stands](#where-each-piece-stands) collects it in one place.

Five Chronicle terms come up throughout:

- An **event sequence** is an ordered log of events; the event log is the default one.
- A **namespace** is a logical partition within an event store.
- An event's **subject** is the identity its personal data is keyed to, normally the person the data is about; it's the event source unless the event or the append names a different one.
- An **observer** processes events, such as a projection, a reducer or a reactor.
- A **partition** is the events of one event source, such as one author, and an observer processes each partition separately.

## Why this shape

Cratis is designed so that the right pattern is the easy one, and developer experience is a design goal. It's also a set of separate products with seams you can open. A header, a generated proxy, a namespace choice, and in the modeling layer a `.play` file: each can be read, diffed and tested on its own. When something breaks between two products, you look at that seam instead of guessing at a framework's internals. A seam is also a place to stop, which is why [When not to use it](#when-not-to-use-it) suggests adopting the boundary you need rather than the whole ecosystem.

A few habits run through every section.

**One decision, in the place that owns it.** The tenant header is set once, in Arc's configuration. The uniqueness rule sits on the event. `[PII]` goes on a value's type, so every event property of that type is encrypted. Validation rules are written once, on the server, and the generated TypeScript carries the subset it can express.

**Commands, events and views do different jobs.** A command can be rejected. An event records something that did happen. A view is derived and can be rebuilt. That split is why a wrong view is a projection fix and a replay rather than a repair script, and why side effects live in reactors and not in projections.

**A fact is not a message.** A notification is sent once, to whoever is listening. A recorded fact stays in the log, so a view built from it can be built again, and a view you add next year can be built from events recorded today.

![A diagram titled A fact is not a message, with two lanes. A notification: an Author row leads to a sent AuthorRegistered, tagged Gone once sent. A recorded fact: a recorded AuthorRegistered leads to a projection and then an Author view, tagged Can be read again.](./fact-not-message.png)

*A notification is gone once sent; a recorded fact can be read again.*

## Model it: write the intent down first

[Event modeling](https://cratis.io/event-modeling/) draws a feature as a timeline of screens, commands, events, read models and automations. For the author feature that timeline is short: a librarian fills in a form, the system records that an author was registered, and a list shows the authors. Drawing it first lets the people involved argue about cause and information flow while changing their minds is still cheap.

![A diagram titled One slice as an event model, drawn as five horizontal lanes. Screen: an Author form issues the RegisterAuthor command, which produces the AuthorRegistered event. AuthorRegistered is projected into the Authors view, which feeds an Author list screen. In the Event log lane, a recorded AuthorRegistered is an instance of the modeled event. A band at the bottom reads: One .play file. The compiler, Stage, Scene and specs read it.](./model-timeline.png)

*One slice as an event model, and the file that holds it.*

An event model on a whiteboard stops matching the code soon after the code exists. [Screenplay](https://cratis.io/screenplay/), experimental like the rest of the modeling layer, writes the model down as a versioned `.play` file next to the code it describes. This invoice slice is from [Why Screenplay](https://cratis.io/screenplay/why-screenplay/). A slice lives inside a module and a feature, so it's shown here with those and with the concepts and policy it refers to:

```text
concept InvoiceId     : Uuid
concept InvoiceNumber : String

policy CanManageInvoice
  require role "InvoiceManager"

module Invoicing

  feature InvoiceManagement

    slice StateChange RegisterInvoice
      command RegisterInvoice
        invoiceId     InvoiceId
        invoiceNumber InvoiceNumber
        authorize CanManageInvoice
        validate
          invoiceNumber matches "^INV-[0-9]{6}$"  message "Must look like INV-000000"
        produces InvoiceRegistered
          invoiceId     = invoiceId
          invoiceNumber = invoiceNumber
          registeredAt  = $context.occurred

      event InvoiceRegistered
        invoiceId     InvoiceId
        invoiceNumber InvoiceNumber
        registeredAt  DateTime
```

The command, who may run it, what it validates and the event it produces sit in one reviewable diff. A declared event is a statement of intent: `AuthorRegistered` in the model says the system is meant to be able to record it. Only the event log says it did.

Checking the model needs nothing running:

```bash
cratis screenplay validate ./plays --warnings-as-errors
```

The CLI compiles every `.play` file under the folder as one application and prints compiler-style errors, so it fits in CI on a machine where the application has never started. It checks the model. Whether a renderer can build it is a separate question. An assistant can work on the same file, and [Automate it](#automate-it-the-life-cycle-when-agents-write-the-code) covers how.

**Starting from a system you already have.** Most systems exist long before anyone models them. [Prologue](https://github.com/Cratis/Prologue), also experimental, stands beside a running system, captures selected database changes, HTTP calls and telemetry metadata, and proposes candidate slices as a `.play` draft. It records metadata rather than row values or request bodies, but metadata can still be sensitive, and its links between events are a time-window guess. The result is a provisional model for a person to correct. It doesn't recover domain truth.

There's one rule in this layer we care about more than any single feature. Producers and consumers of a model have to declare what they can handle and expose what they can't represent, instead of dropping it silently.

## Start it: from nothing to a running skeleton

`cratis new` creates a full-stack skeleton from the [Cratis templates](https://cratis.io/templates/), and the CLI can run them without a .NET SDK installed:

```bash
cratis new cratis --language csharp -n MyApp -o MyApp
```

Swap `csharp` for `kotlin` or `java` for the same full-stack shape on Spring Boot, and pass `--database` for MongoDB, PostgreSQL, SQL Server or SQLite. With the .NET 10 SDK, `dotnet new cratis` from `Cratis.Templates` does the same job. You get Arc, React with Vite and Components with proxy generation configured.

Arc recommends a [vertical slice](https://cratis.io/arc/vertical-slices/): the command, the read model, the screen and the specs in one feature folder, so one change is one diff. Arc doesn't enforce it. We still recommend it. When a feature is spread across five layer folders, reviewing one change means opening all five.

### At the edge: sign-in, tenant and onboarding

[AuthProxy](https://cratis.io/authproxy/) sits in front of the backend and the frontend. It handles [OIDC and OAuth2 sign-in, plus JWT bearer authentication](https://cratis.io/authproxy/configuration/authentication/), resolves a tenant for each request and forwards it downstream in a header named `Tenant-ID`. [Tenant resolution](https://cratis.io/authproxy/configuration/tenancy/) is a list of strategies under `TenantResolutions`, and resolving from a token claim is one entry in it:

```json
{
  "Cratis": {
    "AuthProxy": {
      "TenantResolutions": [
        { "Strategy": "Claim", "Options": { "ClaimType": "tid" } }
      ]
    }
  }
}
```

AuthProxy matches the claim's value against the source identifiers you configure for each tenant. It can also require configured claims, such as a role or a group, before it forwards a request. Let the backend accept traffic from the proxy and nothing else, because a service reachable directly believes whatever headers a caller sends it.

A user who has signed in but belongs to no tenant yet needs somewhere to go. [Ante](https://github.com/Cratis/Ante) is a separate invitation and onboarding lobby for that moment: join an existing tenant, create one by invitation, or self-register. It records the acceptance and publishes it for your application to act on; membership, provisioning and email stay yours. Its docs say it's verified by source-level specs only, with no end-to-end walkthrough yet.

### The command

In Arc, `RegisterAuthor` is a command: a record with a `Handle` method. This one is from the [Arc tenancy docs](https://cratis.io/arc/backend/csharp/chronicle/tenancy/); `AuthorId` and `AuthorName` are the example's own types:

```csharp
[Command]
public record RegisterAuthor(AuthorId Id, AuthorName Name)
{
    public AuthorRegistered Handle() => new(Name);
}
```

That's the whole command. [Arc](https://cratis.io/arc/) gives it an HTTP route and runs validation and declared authorization on it (`[Authorize]`, roles and policies). The handler returns an `AuthorRegistered` event, and the command can append the event it returns. You write no controller, no DTO and no registration list. The name travels as a typed value instead of a bare string. The service code, the authorization policy and the storage stay yours.

Arc reads the tenant from a header too, but its default header name is `x-cratis-tenant-id`, so point it at the proxy's header. The [tenant resolver docs](https://cratis.io/arc/backend/csharp/tenancy/resolvers/) show the setting with a custom name. The extension method lives in `Cratis.Arc.Tenancy`:

```csharp
using Cratis.Arc;
using Cratis.Arc.Tenancy;

builder.AddCratisArc(options =>
{
    options.UseHeaderTenancy("Tenant-ID");
});
```

With the default resolvers, a missing header selects the unset tenant and then Chronicle's default namespace rather than rejecting the request, so decide deliberately whether that's allowed.

### The form

After each build, Arc's proxy generator writes a TypeScript version of the command, and [Components](https://cratis.io/components/) binds a form to it. This is from the Components [form recipe](https://cratis.io/components/building-a-form/). `RegisterAuthor` here is the generated proxy class; nobody writes it by hand:

```tsx
<CommandDialog<RegisterAuthor>
    command={RegisterAuthor}
    title='Add author'
    okLabel='Add'
    initialValues={{ id }}
    validateOn='change'
    onSuccess={() => console.info('Author registered')}
>
    <InputTextField<RegisterAuthor>
        value={(command) => command.name}
        title='Name'
        placeholder='Sample Author'
    />
</CommandDialog>
```

The field accessor is typed against the command. Rename `Name` in C#, rebuild, and that line stops compiling. We generate the proxy for exactly this reason: drift between frontend and backend shows up as a compile error in your own build. **Add** stays disabled until the validation rules the backend shared with the proxy pass, and server messages land on their fields.

The generator carries a supported subset of the rules. Custom predicates and dependency-backed checks are not translated into browser logic. Conditions are not reproduced either: a recognized rule inside a condition can become unconditional on the client. Inspect and test generated validation; the server remains authoritative. A full regeneration clears the proxy output folder, handwritten files included, so give the generator a folder of its own. [The proxy boundary](https://cratis.io/arc/understanding-the-proxy-boundary/) explains what crosses it.

### The rule that holds when it's written

A uniqueness check against a read model races. Two requests in the same second both look, both see no "Jane Austen", and both write.

Chronicle checks [constraints](https://cratis.io/chronicle/constraints/), such as uniqueness, in the kernel when an event is appended, and rejects the append that would break one. This model-bound form is from the constraints docs, so the event is the docs' own:

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Events.Constraints;

[EventType]
public record ConstraintsModelBoundUniqueProjectCreated([property: Unique] string Name, string Description);
```

A constraint is scoped to its event sequence and namespace, and Arc's Chronicle integration maps each tenant to its own Chronicle namespace. So the name is unique within each tenant, which is the rule the sticky note asked for. Nobody wrote a per-tenant uniqueness check. Two pieces of existing behavior, a namespace mapping and a constraint scope, produced it.

### When one event isn't enough

Uniqueness is the easy invariant. "A member can have at most three books on loan" spans many events, and there you have choices. Chronicle supports decisions scoped this way, what the community calls a [dynamic consistency boundary](https://dcb.events/), through constraints, concurrency scopes and, in the .NET client, decision reads.

**Concurrency scopes** make an append fail if matching events were appended since you read. One default to know about: the first append into a scope isn't checked unless you opt in, per append with `ExpectingNoMatchingEvent()` in .NET (the JVM client has an equivalent), or with the `CheckFirstAppendIntoAScope` setting. The TypeScript and Elixir clients can't ask for it. The [concurrency docs](https://cratis.io/chronicle/events/concurrency/) cover the details.

**Decision reads** fold the read model you decided from and guard the append with it. This snippet is from the Chronicle docs, with their order example and the two `using` lines the snippet needs:

```csharp
using Cratis.Chronicle.EventSequences;
using Cratis.Chronicle.ReadModels;

var read = await eventStore.GetDecisionReads().GetDetached<OrderEligibility>(orderId);
if (!read.Exists)
{
    // Decide whether creation is allowed, including the absent case.
}

var result = await eventStore.EventLog.AppendMany(
    [new EventForEventSourceId(orderId, new OrderPlaced())],
    guardedBy: [read]);
var conflicts = result.GetDecisionConflicts([read]);
if (conflicts.Any())
{
    // The decision must be read again and resubmitted; no sequence numbers are exposed.
}
// Check result.IsSuccess separately for constraint violations and other append failures.
```

It's an optimistic guard. It doesn't lock and it doesn't retry. The read model has to be a Chronicle projection keyed directly by the event source, with no joins or children, and the cost grows with that key's history.

**Aggregates**, if you want them, come from Arc rather than Chronicle. This is from Arc's [aggregates docs](https://cratis.io/arc/backend/csharp/chronicle/aggregates/):

```csharp
[Command]
public record WithdrawFunds([Key] Guid AccountId, decimal Amount)
{
    public async Task<AggregateRootCommitResult> Handle(Account account)
    {
        await account.Withdraw(Amount);
        return await account.Commit();
    }
}
```

Arc discovers the aggregate, loads its history for the command's key before `Handle` runs, and commits its events in the command's transaction. Its docs are frank that rehydration alone doesn't prove a concurrency guarantee, and aggregates are C# only today.

![A diagram titled Three ways to guard a rule, three columns side by side. Chronicle, unique constraint: checked in the kernel at append, per event sequence and namespace. Chronicle, decision read: the append is guarded by the read it decided from. Arc, aggregate: loads one key's history and commits in the command. A band underneath reads: All three append to the same event log.](./consistency-choices.png)

*Three ways to guard a rule, from narrowest to most familiar.*

Our opinion: reach for a constraint first, a decision read when the rule really spans events, and an aggregate when your team thinks in aggregates and the boundary is genuinely fixed. Arc's own framing helps here. A read model answers "what does this look like now?" and an aggregate answers "is this change allowed?". They compose: validate against the read model for a fast, friendly message, and let the write side enforce the invariant.

### The view

A [projection](https://cratis.io/chronicle/projections/) turns `AuthorRegistered` events into an `Author` read model. Chronicle projections map matching property names by default, so there's no property-by-property mapping to write where names match. The screen reads that read model through a query, a static method on the read model that Arc also routes. Arc queries can also be observable: the generated React client gets the current result and then supported later updates over WebSocket or Server-Sent Events. The [.NET walkthrough](https://blog.cratis.io/event-sourcing-in-dotnet-with-chronicle/) builds this kind of slice end to end with a runnable project.

### The spec

The [Arc testing docs](https://cratis.io/arc/backend/csharp/testing/chronicle/) have this illustrative spec for a register-author command (their `RegisterAuthor` takes an event source ID and a string):

```csharp
public class when_registering_author : Specification
{
    readonly EventSourceId _authorId = EventSourceId.New();
    readonly CommandScenario<RegisterAuthor> _scenario = new();
    CommandResult _result = default!;

    async Task Because() =>
        _result = await _scenario.Execute(new RegisterAuthor(_authorId, "Jane Austen"));

    [Fact] void should_succeed() =>
        _result.ShouldBeSuccessful();

    [Fact] Task should_have_appended_registered_event() =>
        _scenario.EventLog.ShouldHaveAppendedEvent<AuthorRegistered>(_authorId);
}
```

It runs Arc's command pipeline and an in-memory Chronicle event log in one process, without a Chronicle server. It checks the decision and the recorded fact. HTTP routing, the auth middleware, a real read-model store and redelivery need a different kind of test. [Specifications](https://cratis.io/specifications/) supplies the given/when/then base on xUnit or NUnit, and Synopsis can turn recognized specification shapes into navigable HTML documentation; it doesn't run them.

## Or render it from the model

The experimental [Stage](https://github.com/Cratis/Stage) renderer turns a `.play` model into a reviewable C# application on Arc and Chronicle, so some of the code above doesn't have to be typed at all:

```bash
cratis render ./plays \
  --target cratis \
  --destination ./out \
  --name MyApplication
```

The output is deterministic, down to a manifest of file hashes. It refuses to overwrite a generated file you've edited unless you pass `--force`, and never overwrites a file it didn't generate. It also leaves a `Customizations/` folder that it never reads or touches.

If any part of the model is something the renderer can't express, it reports a blocking diagnostic and publishes nothing.

The `cratis` target is the only one, and it covers a narrow backend vertical: concepts, a command with `not empty` validation, its event, a one-instance projection, a by-key query and generated specs. Events with several generations, bodied reducers and opaque policies are refused for now. A successful render is a plan that validated. It isn't a build or a running application. A second model-led change still needs to be proved against a running target.

Two companions sit beside it. `cratis run ./screenplays` starts a disposable Docker sandbox that loads the model and serves an API, a generated frontend and Chronicle Workbench, so you can poke the model before rendering anything; it doesn't yet enforce the model's command validation or authorization, and it's not for production. The Stage specification runner checks the Given/When/Then examples in the model against the model itself. That's useful, and it's explicitly a different thing from running them against a live system.

## One contract, several ecosystems

Arc's HTTP contract is shared across three server implementations, and each generates TypeScript proxies for the frontend, within the gaps it states. Not every team is on .NET, and not every service in one system should have to be.

On the JVM, [Arc for Kotlin](https://cratis.io/arc/backend/kotlin/) is a Spring Boot implementation for Kotlin and Java, published to Maven Central. This file is from its README:

```kotlin
// src/main/kotlin/example/tasks/CreateTask.kt
package example.tasks

import io.cratis.arc.artifacts.Command
import io.cratis.arc.authorization.AllowAnonymous

data class TaskCreated(val title: String)

@Command
@AllowAnonymous
data class CreateTask(val title: String) {
    fun handle(): TaskCreated = TaskCreated(title)
}
```

Arc derives the route from the package, so the README also sets `cratis.arc.endpoints.segments-to-skip-for-route=2` in `application.properties` to drop `example.tasks` from it. With that setting the command gets `POST /api/create-task`, with validation, authorization, tenancy, observable queries and in-process command scenarios. It doesn't claim parity with .NET: command operations and aggregates aren't in it, and it runs only on Spring Boot.

On Node.js, [Arc for TypeScript](https://github.com/Cratis/Arc.TypeScript), an early source preview, is a TypeScript command and query server; its npm packages are unpublished, and its APIs can still change. A command is a decorated class, as in its Tasks sample:

```typescript
@command()
export class RegisterTask {
    @field(TaskId) id!: TaskId;
    @field(TaskTitle) title!: TaskTitle;

    handle(tasks: Tasks): TaskId {
        tasks.register(this.id, this.title);
        return this.id;
    }
}
```

It has adapters for Express, Fastify and Hono, plus a Fetch API entry for Next.js route handlers, Bun and Deno. Its Chronicle integration is experimental.

Chronicle has its own set of clients. It's an event-sourcing database and processing runtime with a first-class .NET SDK, and clients for TypeScript, Kotlin/Java (JVM) and Elixir. Storage is pluggable, with providers for MongoDB (the default), PostgreSQL, SQL Server and SQLite. Services in one system can use different clients against the same kernel. The clients are not interchangeable, though: the default concurrency check, `ExpectingNoMatchingEvent`, decision reads and some erasure options differ, and [where the clients differ](https://cratis.io/chronicle/clients/where-the-clients-differ/) lists the gaps. [Event sourcing in any language](https://blog.cratis.io/event-sourcing-in-any-language/) explains the shared contract underneath.

## Protect it: personal data, marked once

The author's name is personal data. One attribute on its type makes Chronicle encrypt the value with the key of the event's subject, and with Arc's Chronicle integration the same attribute keeps it out of the causation record. [The log remembers](https://blog.cratis.io/the-log-remembers-pii-crypto-shredding-in-chronicle/) shows the Chronicle side in five languages; here's the short version.

The name's [`ConceptAs<T>` type is marked `[PII]`](https://cratis.io/chronicle/compliance/pii-with-concepts/), and every event property of that type is encrypted for the event's subject. This type is from the PII docs, so its name is the docs' own:

```csharp
using Cratis.Chronicle.Compliance.GDPR;

[PII]
public record PiiConceptsPersonName(string Value) : ConceptAs<string>(Value)
{
    public static readonly PiiConceptsPersonName NotSet = new(string.Empty);

    public static implicit operator string(PiiConceptsPersonName name) => name.Value;
    public static implicit operator PiiConceptsPersonName(string value) => new(value);
}
```

Projection-backed read models track the protected value's subject through their mappings. Reducer read models need their own PII marking, because the kernel can't infer arbitrary transformations.

**Keep it out of the audit trail.** With Arc's Chronicle integration, a command's property values are recorded in the causation of every event it appends, so an unmarked password or token lands in the log in clear text and stays there. Arc leaves `[PII]` values out of that record, and [`[NotAudited]`](https://cratis.io/arc/backend/csharp/attributes/) does the same for secrets without encrypting them. For an operational secret you must store, Chronicle has [`[Encrypted]`](https://cratis.io/chronicle/security/encrypted-values/), with a separate key that erasing a person doesn't touch.

Pick the attribute by what the value is. Personal data you may have to erase gets `[PII]`. A value that should never reach the causation record gets `[NotAudited]`, and an operational secret you have to keep gets `[Encrypted]`.

**Forgetting.** Erasure is one call, from the Chronicle docs' own example:

```csharp
await eventStore.PII.DeleteEncryptionKeyFor("person-42");
```

Successful [key destruction](https://cratis.io/chronicle/compliance/key-lifecycle/) removes Chronicle's decryption path for ciphertext protected by those keys, while preserving the event slot. The event still records that something happened.

Where erasure stops:

- The key belongs to a subject within a namespace. A person who exists in two tenants needs two erasures.
- Values that were never marked stay readable, and so do causation values recorded in clear before anyone marked them.
- A rebuild of a stored read model that covers an erased subject is refused for that subject's partition; authorize a new key for anyone you intend to keep protecting before such a rebuild.
- Restoring a backup from before the erasure brings the key back.
- Copies outside Chronicle, including exported keys, messages sent to another system and values already shown in a browser, need separate handling.

By default Chronicle stores keys with the events; it can keep them in a dedicated store, such as HashiCorp Vault or Azure Key Vault, instead. A restore then has to line up events, keys and certificates to the same point in time, or it can undo an erasure you already reported.

![A diagram titled What deleting a key reaches. A panel labeled Inside Chronicle, namespace Acme holds two cards. Event log: the encrypted value is unreadable; the record remains. Managed read model: the protected field reads empty. A second panel, Deleting the key doesn't reach, holds three cards: backups taken before erasure, copies sent elsewhere, and values already shown. A bottom card, Another namespace, reads: The same person in another tenant needs their own erasure.](./erasure-boundary.png)

*Deleting a person's key reaches the event log and managed read models, not copies.*

These are mechanisms with known edges. An application that handles personal data still needs its own privacy review.

## Run it: tenants and services

### Three tenant boundaries

AuthProxy resolves the tenant at the edge, Arc reads it from a header and checks declared authorization on each command and query, and Arc's Chronicle integration maps each tenant to a Chronicle [namespace](https://cratis.io/chronicle/concepts/namespaces/). Events, observers and read models are processed per namespace.

Selecting a tenant isn't authorizing it. Caller-controlled headers, query strings and hosts aren't evidence of membership, and a wrong but accepted tenant ID selects another namespace, so check membership before any tenant-scoped work and test the no-tenant case. Arc's `/.cratis/me` endpoint tells the frontend who the user is; it doesn't authorize commands or queries.

Where read models land depends on your storage. Arc's MongoDB integration can name a database per tenant, and with EF Core a tenant-specific connection is yours to set up. Work that runs outside a request, such as a scheduled job, has no header to read and must set its tenant explicitly; [Arc tenancy with Chronicle](https://cratis.io/arc/backend/csharp/chronicle/tenancy/) covers both cases.

![A diagram titled Three tenant boundaries, three columns from left to right. Edge, AuthProxy: selects the tenant and forwards it as Tenant-ID. App, Arc: reads a header, configured for Tenant-ID. Store, Chronicle: a namespace per tenant, mapped from Arc's tenant. Below, under Read-model storage: MongoDB, a database per tenant via Arc; EF Core, a connection you configure. A full-width card, Membership: your rule, reads: Check membership before tenant-scoped work. A header or tenant ID is not proof of membership.](./tenant-boundaries.png)

*Selecting a tenant isn't authorizing it.*

### A private fact and a public contract

Say the author feature runs in an Authors service, and a Catalog service needs to hear about new authors. The tempting move is to let Catalog read the Authors service's events. Don't. That couples Catalog to every internal decision the Authors service will ever make.

Chronicle uses a .NET/Orleans actor-based kernel behind gRPC/HTTP surfaces and supports multiple event stores, namespaces, and persistent event-store subscriptions with outbox/inbox sequences. An event store is a natural boundary for one service's data. [Persistent subscriptions](https://cratis.io/chronicle/subscriptions/) carry events from one store's [outbox to another store's inbox](https://cratis.io/chronicle/subscriptions/outbox-inbox/), named after the source. The [architecture overview](https://cratis.io/chronicle/architecture/) shows how the parts fit, and it makes no scale or throughput guarantee. One operational trap is worth knowing before you run more than one server: with the default localhost clustering, two servers pointed at the same database each form their own single-node cluster, and nothing errors at startup.

The Authors service's log holds everything about the registration. Its outbox carries a smaller event you're willing to support as a contract: a new author exists, under this ID, without the name that's personal data. Catalog processes it from its inbox, translates it into a fact of its own, and decides what it means there. When a forwarded event does carry personal data, the subject's key travels with it within the namespace, and erasure covers the stores in that namespace.

![A diagram titled A private fact and a public contract, with two service frames. The Authors service holds an event log with AuthorRegistered, tagged private, and an outbox with AuthorAvailable, tagged public contract; a dashed box between them reads Two separate appends. A persistent subscription carries the outbox event down into the Catalog service's inbox, named after the source, where it is translated into a Catalog-owned fact in the Catalog event log.](./private-fact-public-contract.png)

*A private fact stays in the log; a smaller event is the public contract.*

**The window between two appends.** The untagged [cross-store sample, at commit `95f644d`](https://github.com/Cratis/Samples/blob/95f644dc017ebd6ecd41854cbcd358cb22984084/Chronicle/CrossStore/Program.cs), appends the fact to the source event log, then appends the public event to the outbox as a second call. If the second append fails, the first fact is already recorded; nothing rolls it back. Forwarding isn't a transaction across stores.

One option is a reactor that observes the private fact and appends the public contract, checking the append result and failing the handler on rejection so the partition is retried. Both publisher and receiver must account for duplicate execution. A webhook sends observed events to an HTTP endpoint with retries, so the receiving endpoint needs the same care. Explicit subscriptions exist in each Chronicle client; the attribute-based routing that sets one up implicitly is C# only.

## Debug it: when a view stops updating

An observer that has stopped looks exactly like one with nothing to do. For the author feature, that shows up as an author who registered fine but never appears in the list: the command succeeded, the event is in the log, and the list is wrong.

The read model has the current state and the log has the events behind it. Between them sits an observer that may be working, may be behind, or may have stopped a few events ago. The CLI's README says it plainly: lag is ambiguous, and a failed partition is not.

We built the CLI so you can ask the running system instead of comparing sequence numbers by hand. The [Cratis CLI](https://cratis.io/cli/) provides terminal workflows for inspecting and diagnosing Chronicle, and installs with Homebrew, as a self-contained binary or as a .NET tool. Start with `diagnose`. This output is from the CLI's README, which uses a bookshop rather than our authors:

```text
❯ cratis chronicle diagnose

── Chronicle Diagnostics  14:18:21 ─────────────────────────────────────────────
  server:      chronicle://chronicle-dev-client:***@localhost:35100/
  event store: Bookshop  /  Default

  ✓  Connection            connected
  ✓  Server version        16.7.0
  ✓  Event stores          2 stores: System, Bookshop
  ✓  Observers             9 active
  ✗  Failed partitions     1 need attention  → cratis chronicle failed-partitions list
  ✓  Recommendations       none
  ✓  Event sequence        tail: 22

  ✗ Issues detected — review items above
```

The failing row names the next command, and `diagnose` exits nonzero when failed partitions exist, so it works as a check in a script too. `failed-partitions show` then gives the exception for each attempt:

```text
FailedPartition: caadc869-1251-41d0-9063-6947eaf74043
Observer:        Bookshop.OverdueNotices
Partition:       978-0131177055
Attempts:        5

  --- Attempt at 2026-07-28T12:17:56.6680000+00:00 (Seq# 22) ---
  Exception has been thrown by the target of an invocation.
  smtp.bookshop.local: connection refused
```

The partition is a book's ISBN, because that's the event source ID the application uses. For us it would be the author's ID. Failures are addressed by your own keys, so you can go straight from "this author is missing" to "this author's partition failed, and here's why".

Behind that is Chronicle's failure model. When one partition fails, it stops and is retried with backoff while every other partition keeps going; after the configured number of attempts it's quarantined until someone looks. Fix the cause, then ask for exactly one more attempt:

```bash
cratis chronicle observers retry-partition Bookshop.OverdueNotices 978-0131177055 -y
```

The kernel can refuse a retry, for example on a quarantined observer, and the CLI then exits nonzero with a suggestion. Even a success only says the retry started, so run `diagnose` again.

Our strong advice: retry the partition before you replay anything. `observers replay` is the bigger hammer. It reprocesses the observer from sequence zero and rebuilds its read model, and on a large store it's neither instant nor free.

![A diagram titled Following a failed partition, numbered steps stacked from top to bottom. 1 diagnose: one failed partition; next command named. 2 failed-partitions show: error per attempt, by your key. 3 Fix the cause. 4 retry-partition: one more attempt for that partition. From step 4, one arrow leads to 5 diagnose again, and a second arrow, labeled bigger hammer, leads to observers replay: rebuilds from sequence zero.](./failed-partition-loop.png)

*Inspect, fix the cause, retry one partition, inspect again.*

The rest of the debugging kit, by where you are:

- **In a terminal on a server.** `cratis chronicle workbench` opens a full-screen terminal dashboard over the same connection. `Ctrl+P` searches observers, event types, projections, read models and failed partitions at once. That matters because "author" isn't a name in one list; it's a thread through five of them. Actions such as replaying an observer or retrying a partition sit in place, behind a confirmation dialog. Tab completion asks the live server for observer and read-model names.
- **In a browser.** Chronicle Workbench provides a bundled local browser surface for authorized inspection of Chronicle runtime state and preview of supported projection behavior. The [Workbench docs](https://cratis.io/chronicle/workbench/) cover what it shows.
- **In your editor.** [Narrator](https://github.com/Cratis/Narrator), a VS Code extension we still treat as experimental, browses event stores, event types, read models and observers, and pages through events. It's for reading, not operating.

Some CLI commands change state, replaying an observer and retrying a partition among them, and Workbench has screens for revising and redacting events. Being able to open a tool or run a command isn't permission to use it on a production system.

## Evolve it: four kinds of change in year two

A year in, four kinds of change show up that look alike: a new shape for an event, a new view over old events, a correction to something recorded, and a processor that stopped. Chronicle has a separate mechanism for each, so each is an operation you choose rather than a script you write against the store.

![A diagram titled Four kinds of change, as four cards. A new shape for an event: generations; the stored one is kept. A new view over old events. A processor that stopped. A correction, as four options: reversal, a new event; revision, the original kept; redaction, a marker in the slot; key erasure, values unreadable. A band at the bottom reads: The event log. Only corrections change what it shows.](./day-400-four-changes.png)

*Four kinds of change, and which one touches the log.*

**A new shape.** Chronicle keeps [generations of an event type](https://cratis.io/chronicle/understanding-event-evolution/) side by side, and you declare a migration between adjacent generations. Chronicle produces upcast and downcast representations while keeping the originally stored generation, so old and new code can each read the shape they expect, and a background job migrates existing events. Give long-lived events an explicit ID: event types take their identity from the type name otherwise, so renaming the class changes the identity. If what the event *means* has changed, that's a new event, and a migration is the wrong tool.

**A new view.** When a projection is wrong, fix it and [rebuild the read model](https://cratis.io/chronicle/scenarios/rebuild-a-read-model/) from the retained history. When a projection's definition changes, Chronicle compares it with the previous one and decides between no replay, a partial replay and a full one; a setting chooses whether it runs that work or only recommends it. A replay can repeat a reactor's side effects, and `[OnceOnly]` keeps a reactor out of replays without stopping retries. Retiring a projection leaves its old read-model data for you to remove. Replays, catch-ups and event migrations run as jobs you can inspect, stop and resume, with a setting that caps how many steps run in parallel.

**A correction.** "Fix the data" is four different operations. A business reversal, such as a cancelled registration, is a new event. A mistaken value can be [revised](https://cratis.io/chronicle/events/revision/), keeping the original for audit. [Redaction](https://cratis.io/chronicle/events/redaction/) replaces an event's content with a marker at the same sequence number. Erasing a subject's key makes their marked values unreadable. Redaction doesn't clean up copies in other stores, backups or anything already read, and an observer only hears about it if it subscribes to the redaction event as well as the original.

**A processor that stopped** is the debugging loop above, and the [troubleshooting guide](https://cratis.io/chronicle/troubleshooting/) walks it end to end.

## Automate it: the life cycle when agents write the code

An agent can draft the `RegisterAuthor` command, its projection and its spec in a few minutes. Once that's true, typing is no longer the slow part of shipping the author feature. The slow parts sit on either side of it: saying precisely what should be built, and checking that what came back is that.

People have started calling the result an agentic development life cycle, or ADLC. The published versions disagree on the stages, but they share one idea: the familiar stages stay, and each one has to hand the next something an agent can read and a person can check.

The most useful critique we've read comes from the spec-driven development side. In her [look at three spec-driven tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) on martinfowler.com, Birgitta Böckeler separates three levels. Spec-first writes a spec to guide one change. Spec-anchored keeps the spec and evolves it with the feature. Spec-as-source makes the spec the only thing people edit. She finds the markdown these tools produce can be harder to review than the code, and she wonders whether spec-as-source, and even spec-anchored, could end up with the downsides of both model-driven development and language models: inflexibility and non-determinism.

We sit at spec-anchored, with a spec a compiler reads. The event model is the spec and the `.play` file is its text. Its commands, events and projections are the concepts Arc and Chronicle run, so the spec and the running system share one vocabulary. For the narrow part Stage can render, it moves a step toward spec-as-source. A textual model with a code generator is the model-driven shape she warns about. The renderer is deterministic, so that step adds no unpredictability of its own, but the rigidity risk applies to us, and the next section shows where hand-written code goes.

![A diagram titled The agentic loop, seven numbered cards in a loop. Top row, left to right: 1 Intent: event modeling, Prologue draft. 2 Model: .play file, Screenplay MCP. 3 Code: Stage render, AI corpus. 4 Checks: compiler, analyzers, hooks. An arrow leads down to the bottom row, right to left: 5 Review: pull request, a person decides. 6 Run: Arc and Chronicle. 7 Evidence: event log, CLI, Chronicle MCP. An arrow labeled next change leads from 7 back up to 1.](./agentic-loop.png)

*One pass around the loop, and the Cratis piece at each step.*

The rest of this section walks that loop once with the author feature. Most of what's in it is experimental or early, and each step says so.

### Intent becomes a model

A person decides what should exist; here, that's the sticky note. Written as a slice, it becomes something an assistant and a reviewer both read, and `cratis screenplay validate` checks it before anything runs.

An assistant works on that file through the Screenplay MCP server. It can list the slices that have no `then` assertion or prepare a model-aware rename. Proposals are tied to the revision they were made against, and only an explicit `apply` (or workspace recovery) writes files, which is exactly where your client's approval prompt belongs. None of its tools run specifications.

For a system that already exists, the Prologue draft from [Model it](#model-it-write-the-intent-down-first) enters the loop at the same point, as a proposal a person corrects.

We're building Cratis Studio: an experimental, collaborative place where people and AI design, visualize and edit the same event model.

### The model becomes code

There are two routes from the model to code today.

For the narrow backend vertical Stage supports, `cratis render` writes it, as [Or render it from the model](#or-render-it-from-the-model) describes. What matters for an agent is the seam. The renderer owns the files in its manifest, refuses to overwrite one that was edited, and never reads or touches `Customizations/`. Code written by hand, by a person or an agent, belongs in that folder. An edit to a generated file then shows up as a refused render instead of a silent overwrite, unless someone passes `--force`.

Outside that vertical, the model is the map and an agent writes the code by hand, guided by the Cratis AI corpus: a free, MIT-licensed set of rules, skills, agents and prompts for building with Cratis. [`cratis ai install`](https://cratis.io/ai/getting-started/) installs it into your repository once and points each supported assistant at it:

```bash
cratis ai install \
  --harnesses claude,codex,copilot,cursor,opencode,pi \
  --profiles cratis/application/csharp,cratis/documentation \
  --languages csharp,typescript
```

It records the selection and file hashes, refuses to overwrite files you own, and `cratis ai status` tells you when managed files were edited. That gives an assistant context about how Cratis is meant to be used, with dozens of skills for commands, projections, reactors, concepts and specs. It doesn't give it access to anything, and it doesn't make its output correct.

### Checks that run whether the agent listened or not

Böckeler also notes that agents often ignore the instructions they're given, and asks whether all those files and checklists give a "false sense of control". A rules file is advice. What holds is a check that runs either way, and the author feature meets several:

- `cratis screenplay validate` rejects a broken model before any code exists, and the Stage specification runner checks the model's Given/When/Then examples against the model.
- The compiler and the generated TypeScript proxies turn a renamed field into a compile error on both sides.
- Arc and Chronicle's .NET client ship Roslyn analyzers that report some misuses of their APIs as build diagnostics. They aren't specific to agents; they treat an agent's code like anyone else's.
- The corpus ships hooks that run inside the assistant's own tool.

The hooks are the part written with agents in mind. After an edit, a scan points out patterns the rules warn against, without blocking anything. A guard blocks the store-changing `cratis chronicle` commands it can see in the assistant's shell commands. In Claude Code, when the assistant tries to finish and relevant files have changed, a quality gate runs, and a failure goes back to the assistant instead of letting it stop. In Pi, the gate doesn't run on its own: it's a tool called at a verification checkpoint, and a gate that times out or is cancelled reports that nothing was verified, never a pass. The gates are data a repository can override. Today the hooks are wired for Claude Code and Pi; other assistants get the rules and skills without them.

The same rule shows up elsewhere in this post. `diagnose` exits nonzero when it finds failed partitions, and a render that can't express the model publishes nothing. In each case, a problem or an unfinished check doesn't come back as success.

None of this proves the feature does what the sticky note asks. A green build says the code has the right shape, and [the spec](#the-spec) checks one example of the behavior.

### A person reviews and merges

Reviewing a pull request an agent wrote is a different job from reviewing a colleague's. [One recent piece on it](https://tianpan.co/blog/2026/04/27/reviewing-agent-prs-different-not-faster) makes two points we agree with: the intent sits in a prompt that rarely travels with the pull request, and tests the same agent wrote tend to share its blind spots.

The loop gives the reviewer the intent as a diff of its own. A change to the author feature can arrive as a `.play` change that states the command, its rules and its event, a render manifest that says which files are generated, and code in one feature folder. The reviewer reads the intent first, then checks the code against it.

A proposal, a declared model, a passing specification and a recorded event answer different questions: what was proposed, what the model declares, what a specification checks, and what the running system recorded. A passing spec doesn't approve a proposal or prove deployed behavior.

With the author feature: an assistant's diff that stops two authors in tenant Acme registering under the same name is a proposal. The rule written into the event model is a declaration. A spec that registers the same name twice and expects a rejection checks one example. The event log in Acme's namespace shows what was actually recorded. Someone writes the first three; the fourth is what happened. In a review, it helps to say which of the four you're looking at.

![A diagram titled Four kinds of evidence, four boxes in a two-by-two grid with no arrows between them. Proposal: what was proposed? An assistant's diff. Declaration: what does the model declare? The event model. Spec result: what did a spec check? Same name twice. Observation: what was recorded? Acme's event log.](./four-kinds-of-evidence.png)

*A proposal, a declaration, a spec result and a recorded event answer different questions.*

However a pull request was produced, whether it merges is a person's decision. The corpus's own pull-request rule lets an assistant take a change through to merge only when a person asks it to ship, and even then it stops before a major release until a person explicitly confirms the break.

We're building Cratis Direct: it turns repository signals into one prioritized queue of bounded AI work, and brings the results back as pull requests for people to review. It is an internal experiment the team uses on its own work. Its landing page is [cratis.direct](https://cratis.direct).

![A diagram titled Where people decide, three horizontal lanes across five stage columns: Intent, Model, Code, Review and Run. Lane A person: decides what starts; applies a proposal; decides the merge. Lane Checks: validate and model specs; build, analyzers, hooks; diagnose exit code. Lane An agent: proposes model changes; writes code; reads the event log.](./where-people-decide.png)

*The decisions stay with people; the checks don't take the agent's word for it.*

### Run it, read the log, start again

Once the feature runs, an assistant that helps operate it needs to know which of its actions change anything. `cratis llm-context` prints the CLI's command catalog as JSON, and every command states its effect, `read-only`, `local`, `mutating` or `destructive`, and whether it requires confirmation. An agent can tell observing commands from state-changing ones without keeping its own list. `cratis init` writes that catalog into context files for the tools you use; refresh it after upgrading. Only the effect and confirmation fields are declared stable; bind anything else to the exact CLI version.

[Chronicle MCP](https://cratis.io/chronicle-mcp/) connects an assistant to a running Chronicle server, whatever client language the application uses. It can list observers and failed partitions, read events and read-model instances, describe event types and explain a causal trace. It can also list event types that nothing consumes. The only tools that change anything are three for stopping, resuming and deleting jobs. It can't append, redact or replay.

That makes it a good second pair of eyes on the debugging loop, with a sharp caveat: an assistant connected to it can read event payloads, including personal data. Don't treat it as read-only, scope what you connect it to, don't rely on its development-default credentials, and treat anything it reads as data, not instructions.

![A diagram titled What an agent can reach and change, four columns from left to right. Reads: rules and skills; CLI, read-only commands; Chronicle MCP, events, read models. Proposes: Screenplay MCP, proposals; pull request, code for review. Changes: apply, writes model files; CLI, mutating, destructive, confirmation flagged; Chronicle MCP, stop, resume, delete jobs. A person: decides the merge; decides what starts. A note below reads: Chronicle MCP can't append, redact or replay.](./agent-reach.png)

*What an agent can read, propose and change, and what stays with a person.*

The loop closes at the event log. The model says what the system is meant to record, and the log says what it did record. An event type nothing consumes, a partition that keeps failing, or a causal trace that surprises someone is the input to the next change. None of the public tools here turns that finding into work on its own: an agent can read it, and a person decides what starts.

For questions about the docs themselves, [Prompter](https://github.com/Cratis/Prompter), which we still treat as experimental, answers in Discord with citations you can follow, or declines when it can't ground an answer.

This section argues from structure, not results. We haven't measured whether agents working this loop ship fewer defects or ship faster, and we don't claim they do. The generated vertical is narrow, and a second model-led change hasn't been proved against a running target, so the model anchors the code without replacing it. The hooks cover two assistants, and nothing here guarantees what an agent writes. The [AI assistant walkthrough](https://blog.cratis.io/from-zero-to-first-projection-with-an-ai-assistant/) shows one of these tools on a real task, including where the assistant was told not to use one.

## When not to use it

The strongest argument against all of this is that you can assemble every piece from well-known parts: an identity provider at the edge, a web framework, a database, OpenAPI generation for the frontend, a test runner and a diagram tool. Each part is widely understood, and you avoid tying the application to one vendor's set of products. If your team already has those seams under control and your data's history carries little business meaning, that's a reasonable choice. Our answer is narrower: adopt the boundary you need, together with its dependencies, rather than the entire ecosystem.

Some systems don't need the event history at all. For a small current-state form where nobody needs the story of changes, use a database and keep the extra model, migrations and replay machinery out of the way. Arc works without Chronicle. Chronicle's docs have a page on [when to use event sourcing](https://cratis.io/chronicle/concepts/when-to-use-event-sourcing/), and Screenplay is the wrong tool for a slice that's mostly custom code.

Keeping facts also comes with a bill. Someone owns the old event schemas, the lag between write and read, the identity that makes side effects safe to repeat, the replay decisions and matching restore sets. The year-two section above goes through each of those.

- **Event history:** follow [Get started with Chronicle](https://cratis.io/chronicle/get-started/), append a few events and open the [Workbench](https://cratis.io/chronicle/workbench/).
- **Operating it:** `brew tap cratis/cratis && brew install cratis`, then `cratis chronicle diagnose`, and keep `retry-partition` ahead of `replay` in your runbook.
- **Personal data:** mark one value's type `[PII]`, then read [The log remembers](https://blog.cratis.io/the-log-remembers-pii-crypto-shredding-in-chronicle/).
- **With an assistant:** run `cratis ai install` for the harnesses, profiles and languages you use, keep `cratis screenplay validate` and your build in the assistant's loop, and review its work as a proposal, a model, a spec and the event log.
