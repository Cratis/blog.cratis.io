Take a feature that fits on a sticky note. A signed-in user registers an author, and author names have to be unique within the user's organization.

Before it ships, that feature asks a lot of questions. Who is this user, and which tenant are they in? Are they allowed to register authors? Where does the uniqueness rule live, and does it hold when two requests arrive in the same second? What gets recorded, and what does the screen show? The author's name is personal data, so how does it get forgotten when someone asks? When a second service needs to know about new authors, what does it get? And a year later, when the event needs a new field and one view has stopped updating, how do you find out why?

These questions can span different tools and owners.

Cratis has products at each of those points: an edge proxy, an application framework, an event store with clients in several languages, tools for the running system, experimental modeling, and assistants. Event sourcing is one strand. Arc does not require event sourcing, and Chronicle can be used without Arc. Other pieces have their own dependencies and adoption boundaries.

This article follows the author feature through them, then examines identity and tenants, personal data, developer experience, services, and changes in the second year. The [ecosystem at a glance](https://blog.cratis.io/the-cratis-ecosystem-at-a-glance/) post is the product list; this one is about the joins.

## Hard problems, and what you no longer write

Cratis is designed so that the right pattern is the easy one, and developer experience is a design goal. Here are thirteen hard problems, the Cratis mechanism for each, and what you no longer write. Every mechanism has an edge; the section that covers it states that edge once.

1. **The frontend drifts from the backend.** After each build, Arc's proxy generator writes TypeScript for your commands and queries, and the React code compiles against it. No hand-written client or fetch wrapper, and a renamed field shows up in the frontend build once the proxies are regenerated.
2. **Every operation needs a controller.** An Arc command is a `[Command]` record with a `Handle` method, and a query is a static method on its `[ReadModel]`. Arc finds both, gives each an HTTP route and runs validation and declared authorization on it. No controllers, DTOs or registration lists.
3. **Validation lives in two places.** A command validator runs on the server before `Handle`, and the proxy generator emits a supported subset of its rules, without their conditions, into the generated TypeScript the form uses. Those rules aren't written twice, and the server stays authoritative.
4. **Personal data sits in a log you keep.** Mark a value's type `[PII]` once: Chronicle encrypts every event property of that type with the key for the event's subject, and Arc keeps it out of the recorded causation. No per-field encryption code, and deleting the subject's key removes Chronicle's decryption path.
5. **A uniqueness check races.** Chronicle checks a `[Unique]` constraint when the event is appended, within the event sequence and namespace, and rejects an append that would break it. No lookup before the write, and no lock around it.
6. **A wrong view needs a repair script.** Fix the projection, and Chronicle rebuilds the read model by replaying the retained events; the events stay as they were. Where the event and the read model share property names, the projection maps them by default. No repair script for derived data.
7. **An event needs a new shape.** Chronicle keeps generations of an event type side by side, runs the migration you declare between adjacent generations, and keeps the stored generation. No one-off script that rewrites the store.
8. **Tenants need separate data.** Arc's Chronicle integration maps the current tenant to a Chronicle namespace by default, and Chronicle processes events, observers and read models per namespace. No tenant filter in each event query; you point Arc at the header that carries the tenant, and membership stays your rule.
9. **Services couple through their internals.** Chronicle carries the events you put in one store's outbox to another store's inbox through a persistent subscription. No relay between the two stores, and the events you don't publish stay in your own log.
10. **Every service is pushed onto one stack.** One Chronicle kernel has a first-class .NET SDK plus TypeScript, Kotlin/Java and Elixir clients, with Python coming soon, and storage providers for MongoDB, PostgreSQL, SQL Server and SQLite; Arc runs on .NET and on the JVM. Services can use different Chronicle clients against the same kernel, and each Chronicle deployment chooses its storage provider.
11. **You can't see why a view stopped.** Workbench shows Chronicle's runtime state in a local browser, and `cratis chronicle` lists failed partitions with their attempt count and shows the error for each attempt. No ad-hoc queries against the storage to find out what the event store is doing.
12. **Tests need the whole stack running.** A `CommandScenario` spec runs Arc's command pipeline against an in-memory Chronicle event log in one process, picked up because the testing package is referenced. No registration code and no fake event log.
13. **Assistants guess at your conventions.** `cratis ai install` puts Cratis rules and skills into your repository, with adapters for Claude, Codex, Copilot, Cursor, OpenCode or Pi, chosen by profile and language. Experimental Screenplay MCP lets an assistant propose model changes for you to review, and Chronicle MCP lets it read a running event store. The conventions aren't retyped into each assistant's instructions.

The model can live in the repository too: event modeling is the method, and experimental Screenplay writes it down as a versioned `.play` file that a compiler checks.

### Sign-in and the tenant

AuthProxy signs the user in and resolves their tenant, then forwards it downstream in a `Tenant-ID` header. Arc reads the tenant from a header too; the identity section shows how to point it at `Tenant-ID`.

### The form and the command

In Arc, `RegisterAuthor` is a command: a record with a `Handle` method. Arc gives it an HTTP route and runs validation and authorization on that route. The name travels as a typed value in the command instead of a bare string.

After each build, Arc's proxy generator writes a TypeScript version of the command, so the React code is type-checked against the backend's contract. [The proxy boundary](https://cratis.io/arc/understanding-the-proxy-boundary/) page explains what crosses it.

### The tenant and the namespace

An application can choose a Chronicle namespace per tenant. That choice scopes the rule in the next step.

### The fact, and the rule that holds when it's written

The handler returns an `AuthorRegistered` event, and the command can append the event it returns. A uniqueness check against a read model races: two requests in the same second can both pass it before either writes.

Chronicle checks [constraints](https://cratis.io/chronicle/constraints/), such as uniqueness, when an event is appended, and rejects the append if it would break one. This model-bound form is from the constraint docs:

## Identity and tenants: who decides what

AuthProxy handles sign-in and tenant selection at the edge, Arc checks declared authorization on each command and query route, and an application can choose a Chronicle namespace per tenant. Two joins between them are settings you make, and tenant membership stays your rule.

### At the edge

AuthProxy handles [OIDC and OAuth2 sign-in, plus JWT bearer authentication](https://cratis.io/authproxy/configuration/authentication/), and resolves a tenant for each request. [Tenant resolution](https://cratis.io/authproxy/configuration/tenancy/) from a token claim is a few lines of configuration:

```json
{
  "Strategy": "Claim",
  "Options": {
    "ClaimType": "tid"
  }
}
```

AuthProxy forwards the resolved tenant to downstream services in a header named `Tenant-ID`. It can enforce configured admission claims before forwarding a request. Let the backend accept traffic from the proxy and nothing else, because a service reachable directly believes whatever headers a caller sends it.

### The header hop

Arc also reads the tenant from a header, and its default header name is `x-cratis-tenant-id`. Configure Arc to read the proxy's tenant header and decide whether default-namespace access is allowed. With the default resolvers, a missing header selects the unset tenant and then Chronicle's default namespace rather than rejecting the request.

The [tenant resolver docs](https://cratis.io/arc/backend/csharp/tenancy/resolvers/) show the setting with a custom header name:

```csharp
builder.AddCratisArc(options =>
{
    options.UseHeaderTenancy("X-Custom-Tenant");
});
```

Pass the header name your proxy forwards, which for AuthProxy is `Tenant-ID`.

### At the operation

Arc evaluates [authorization](https://cratis.io/arc/backend/csharp/asp-net-core/authorization/) on the command or query route: `[Authorize]`, roles and policies. Arc's `/.cratis/me` endpoint tells the frontend who the user is; it does not authorize commands or queries. The [auth and compliance](https://cratis.io/auth-and-compliance/) page shows how AuthProxy and Arc divide that work.

### The tenant in the event store and the read models

Inside Chronicle, [namespaces](https://cratis.io/chronicle/concepts/namespaces/) are a logical partition within an event store; events, observers and read models are processed per namespace. Caller-controlled headers, query strings and hosts are not evidence of membership, and a wrong but accepted tenant ID selects another namespace, so check membership before any tenant-scoped work and test the no-tenant case.

Where read models land depends on the storage you pick. Arc's MongoDB integration can name a database per tenant through its resolver. With EF Core, a tenant-specific connection is yours to set up. If you query a read-model database directly, outside Arc and Chronicle, check your provider's naming rules first, because the default namespace doesn't always map to the name you'd guess.

Work that runs outside a request, such as a scheduled job or something a reactor starts later, has no request header to read, so it establishes its tenant explicitly. The [Arc tenancy with Chronicle](https://cratis.io/arc/backend/csharp/chronicle/tenancy/) page covers both the request and the background case.

![A diagram titled Three tenant boundaries. Three stacked boxes. Selection at the edge: AuthProxy resolves a tenant. Carry in the application: Arc reads a configured header. Partition in the event store: a Chronicle namespace the application chooses. Below them, under Read-model storage, two boxes: MongoDB, a database per tenant via Arc's resolver; and EF Core, a connection you configure. ### Views onto the running system

Some tools open a window onto a running Chronicle. Workbench is for authorized inspection and projection preview, and the [Workbench docs](https://cratis.io/chronicle/workbench/) cover what it shows. Some CLI commands change state, replaying an observer and retrying a partition among them, and Workbench has screens for revising and redacting events. Being able to open a tool or run a command isn't permission to use it on a production system.

## Personal data: mark once, encrypt per person

One attribute on a type makes Chronicle encrypt that value with the key of the event's subject, normally the person, and with Arc's Chronicle integration the same attribute keeps it out of the causation record. Deleting that key makes those values unreadable in Chronicle, and where that stops is listed below.

The author's name is personal, so [its `ConceptAs<T>` type is marked `[PII]`](https://cratis.io/chronicle/compliance/pii-with-concepts/) and every event property of that type is encrypted for the event's subject. Projection-backed read models track the protected value's subject through their mappings. Reducer read models need appropriate PII marking because the kernel cannot infer arbitrary transformations. [The log remembers](https://blog.cratis.io/the-log-remembers-pii-crypto-shredding-in-chronicle/) shows the Chronicle side in five languages. What's new here is what Arc adds on top.

![A code card titled Mark the type once, labeled Chronicle and C#, with the caption: Every event property of this type is encrypted for the event's subject. The code reads: using Cratis.Chronicle.Compliance.GDPR; then [PII] on public record PiiConceptsPersonName(string Value), a ConceptAs of string, with a static readonly NotSet value of string.Empty and implicit operators converting to and from string.](./code-pii-concept.png)

<details>
<summary>Show the code</summary>

```csharp
using Cratis.Chronicle.Compliance.GDPR;

[PII]
public record PiiConceptsPersonName(string Value) : ConceptAs<string>(Value)
{
    public static readonly PiiConceptsPersonName NotSet = new(string.Empty);

    public static implicit operator string(PiiConceptsPersonName name) => name.Value;
    public static implicit operator PiiConceptsPersonName(string value) => new(value);
}
```

</details>

### Keep it out of the audit trail

With Arc's Chronicle integration, a command's property values are recorded in the causation chain of every event it appends, so an unmarked password or token lands in the log in clear text and stays there.

Arc leaves `[PII]` values out of that chain, and a second attribute, [`[NotAudited]`](https://cratis.io/arc/backend/csharp/attributes/), does the same for secrets without encrypting them. For an operational secret that has to be stored, Chronicle has [`[Encrypted]`](https://cratis.io/chronicle/security/encrypted-values/). It uses a separate key: erasing a subject's `[PII]` key leaves an `[Encrypted]` value readable, and Chronicle's subject-erasure operation refuses to delete its key.

So: `[PII]` for personal data you may have to erase, `[NotAudited]` for a value that should never reach the causation record, `[Encrypted]` for an operational secret you must keep.

### Forgetting, and where it stops

Successful [key destruction](https://cratis.io/chronicle/compliance/key-lifecycle/) removes Chronicle's decryption path for ciphertext protected by those keys, while preserving the event slot. The event still records that something happened.

Where erasure stops:

- The key belongs to a subject within a namespace. A person who exists in two tenants needs two erasures.
- Values that were never marked stay readable, and so do causation values that were recorded in clear before anyone marked them.
- Restoring a backup from before the erasure brings the key back.
- Copies outside Chronicle—including exported keys, messages to another system and values already rendered in a browser—require separate handling.

By default Chronicle stores the keys in the same storage as the events; it can keep them in a dedicated store, such as HashiCorp Vault or Azure Key Vault, instead. A restore then has to line up the event data, the key store and the certificates to the same point in time; a restore in the wrong order can undo an erasure you already reported.

![A diagram titled Where the key applies, labeled Chronicle, with three groups. Inside Chronicle, namespace Acme: the event log, where the encrypted value is unreadable and the record and ciphertext remain; and a managed read model, where the protected field reads empty and the record remains. Another namespace: the same person in another tenant needs its own erasure. Outside Chronicle: backups taken before the erasure, copies sent to other systems, and values already shown in a browser.](./erasure-boundary.png)

These are mechanisms with known edges, and an application that handles personal data still needs its own privacy review. Redaction and revision, which change an event instead of a key, are in the day 400 section.

## Developer experience: one decision in the place that owns it

For model-bound commands and queries, you don't write controllers, DTOs, fetch wrappers or registration lists, and projections don't need property-by-property mappings where names match. Each convention makes one decision in the place that owns it, and each edge is stated where it applies.

### Commands without the plumbing

This is an Arc command from the [commands page](https://cratis.io/arc/backend/csharp/commands/); `Sku`, `Quantity`, `CartLineId` and `ICartService` come from the surrounding example:

```csharp
using Cratis.Arc.Commands.ModelBound;

[Command]
public record AddItemToCart(Sku Sku, Quantity Quantity)
{
    public CartLineId Handle(ICartService carts) => carts.AddItem(Sku, Quantity);
}
```

Arc gives it an HTTP route and runs validation and authorization, and the build generates the TypeScript that calls it, so there is no controller, DTO or fetch wrapper to keep in step. The service, the authorization policy and the storage stay yours.

### Validation, twice, from one source

A command validator runs on the server before `Handle`. The proxy generator carries the rules it can express into the generated TypeScript, so the form can flag an empty name before the request goes out. Custom predicates and dependency-backed checks are not translated into browser logic. Conditions are not reproduced either: a recognized rule inside a condition can become unconditional on the client. Inspect and test generated validation; the server remains authoritative.

### Generated files belong to the generator

A full regeneration clears the proxy output folder, handwritten files included, so give the generator a folder of its own.

### Names do the mapping

Chronicle projections map matching property names by default; when names differ, you write the mapping.

Event types take their identity from the type name unless you give them one, so renaming the class changes the identity while the stored events keep the old one. Give long-lived events an explicit ID. When you add a generation, the analyzer [CHR0037](https://cratis.io/chronicle/code-analysis/chr0037/) flags generations whose IDs don't match.

## Services and distribution: a private fact, a public contract

Chronicle carries the events you choose from one event store's outbox to another's inbox, so a service shares a contract instead of its internal history, in whichever Chronicle client each service uses. One window, between two appends, is yours to design for. Inside one store, the kernel can place event sequences and observers across the nodes you configure, and a failed partition is retried without holding up the rest.

Chronicle uses a .NET/Orleans actor-based kernel behind gRPC/HTTP surfaces and supports multiple event stores, namespaces, and persistent event-store subscriptions with outbox/inbox sequences. The [architecture overview](https://cratis.io/chronicle/architecture/) shows how the parts fit around the kernel, and it makes no scale or throughput guarantee.

### A private fact and a public contract

In Chronicle, an event store is a natural boundary for one service's data. [Persistent subscriptions](https://cratis.io/chronicle/subscriptions/) carry events between stores through [outbox and inbox sequences](https://cratis.io/chronicle/subscriptions/outbox-inbox/): the source writes to its outbox, and the target receives the events in an inbox sequence named after the source.

The pattern that makes this worth doing is keeping two kinds of event apart. A service's own facts stay in its event log. A smaller event, one you're willing to support as a contract, goes in the outbox. The receiving store processes it from its inbox, translates it into a fact of its own, and decides what it means there. For the author feature, the log might hold everything about the registration, while the outbox carries only that a new author exists and under which ID, not the name that's personal data. When a forwarded event does carry personal data, the subject's key travels with it within the namespace, and erasure covers the stores in that namespace.

![A diagram titled A private fact and a public contract, labeled Chronicle. The Lending event store holds an event log with AuthorRegistered, tagged private, and an outbox with AuthorAvailable, tagged public contract, with the note two separate appends between them. An arrow labeled persistent subscription runs from the outbox down into the Catalog event store's inbox, named after the source. Inside the Catalog store, the inbox is translated into a Catalog-owned fact in its event log.](./private-fact-public-contract.png)

### The window between two appends

The untagged [cross-store sample, at commit `95f644d`](https://github.com/Cratis/Samples/blob/95f644dc017ebd6ecd41854cbcd358cb22984084/Chronicle/CrossStore/Program.cs), shows the pattern and its two-append gap. It appends the order to the source event log, then appends the public event to the outbox as a second, separate call. If the second append fails, the first fact is already recorded; the sample returns an error, and nothing rolls the first append back. Forwarding isn't a transaction across stores.

One option is a reactor that observes the private fact and explicitly appends the public contract to the outbox. It must check the append result and fail the handler on rejection so the partition can be retried. Both publisher and receiver must account for duplicate execution.

### Failure and retries

Each observer tracks its position and processes events per event-source partition. When one partition fails, that partition stops and is retried with backoff while the others keep going. After the configured number of attempts, the partition is quarantined until someone looks at it.

A timeout abandons the wait, not necessarily the work, so the handler may still be running when the kernel retries it. Chronicle's [delivery identity](https://cratis.io/chronicle/reactors/delivery-identity/) gives a handler with side effects something to deduplicate on. For a system that isn't a Chronicle store, a [webhook](https://cratis.io/chronicle/webhooks/) sends observed events to an HTTP endpoint with retries, so the receiving endpoint needs the same care.

### More than one node, and background work

A multi-node setup is a deliberate configuration. With the default localhost clustering, two servers pointed at the same database each form their own single-node cluster, and nothing errors at startup. The [clustering configuration](https://cratis.io/chronicle/hosting/configuration/clustering/) covers membership and the IDs every node has to agree on.

Replays, catch-ups and event migrations run as [jobs](https://cratis.io/chronicle/jobs/) you can inspect, stop and resume, with a setting that caps how many steps run in parallel. Materialized read models update after the append, so a read right after a write can see the old state. You can wait for the observers to catch up, at the cost of latency for that caller.

### Across languages

Services can use different Chronicle clients. Explicit subscriptions exist in each client; the attribute-based routing that sets one up implicitly is C# only. One kernel contract doesn't make the client APIs interchangeable; [where the clients differ](https://cratis.io/chronicle/clients/where-the-clients-differ/) lists the gaps. [Event sourcing in any language](https://blog.cratis.io/event-sourcing-in-any-language/) explains the shared contract underneath.

![A diagram titled One kernel, your language, labeled Chronicle. Under Clients, a group of C#, TypeScript, Kotlin/Java and Elixir connects to the Chronicle kernel through the server contract. The kernel stores through server config to the providers under Storage: MongoDB (default), PostgreSQL, SQL Server and SQLite.](./clients-kernel-storage.png)

All of this gives the boundary between two stores a name and a place in the data, whether you run one service or ten.

## Day 400: four kinds of change

A year in, four kinds of change show up that look alike: a new shape for an event, a new view over old events, a correction to something recorded, and a processor that stopped. Chronicle has a separate, built-in mechanism for each, so each change is an operation you choose rather than a script you write against the store.

![A diagram titled Four kinds of change, labeled Chronicle. A new shape for an event: generations and a migration job; the stored generation is kept. A new view over old events: compared, then no, partial or full replay; the view is rebuilt, the log is not. A correction, as four options: compensation, a new event; revision, the original kept for audit; redaction, a marker in the same slot; key erasure, marked values unreadable. A processor that stopped: a failed partition is retried or quarantined; a retry can be refused. A band at the bottom reads: The event log. Every change reads from it; only corrections change what it shows.](./day-400-four-changes.png)

### A new shape for an event

Chronicle keeps [generations of an event type](https://cratis.io/chronicle/understanding-event-evolution/) side by side, and you declare a migration between adjacent generations. The base class refuses a migration whose two generations don't share an event type ID, or that skips a generation. With migrations declared between generations, Chronicle produces upcast and downcast representations while retaining the originally stored generation, so code can read the shape it expects. Existing events are migrated by a background job.

A migration changes how an event is represented. If what the event means has changed, that's a new event, and a decision for whoever owns the model.

### A new view over old events

When a projection mapping is wrong, fix it and [rebuild the read model](https://cratis.io/chronicle/scenarios/rebuild-a-read-model/) by replaying the retained history. Replay reprocesses the event content Chronicle exposes, including applicable revisions and redaction markers. What it rebuilds is derived state; it doesn't prove that an email went out, which is why side effects live in reactors and not in projections.

When a projection's definition changes, Chronicle compares it with the previous one and decides between no replay, a partial replay and a full one, and a setting chooses whether it runs that work or only recommends it. Retiring a projection unsubscribes it and leaves its old read-model data in place for you to remove. A replay can repeat a reactor's side effects, and `[OnceOnly]` keeps a reactor out of replays without stopping retries.

### A correction to something recorded

"Fix the data" can mean four different operations, and they answer different questions.

- A business reversal, such as a cancelled registration, is a new event. Nothing earlier changes.
- A mistaken value can be [revised](https://cratis.io/chronicle/events/revision/): the corrected content is recorded, and the original is kept for audit.
- [Redaction](https://cratis.io/chronicle/events/redaction/) replaces an event's content with a marker at the same sequence number.
- Erasing a subject's key makes that person's marked values unreadable, as above.

Redaction doesn't clean up copies in other stores, backups or anything already read, and an observer only hears about it if it subscribes to the redaction event as well as the original.

### A processor that stopped

Chronicle records each failed partition with its error and attempt count. `cratis chronicle` can ask for a retry, and the kernel can refuse one, for example on a quarantined observer. The CLI then exits nonzero with a suggestion. Even a success only says the retry *started*. The [troubleshooting guide](https://cratis.io/chronicle/troubleshooting/) walks the loop: inspect, fix the cause, retry or replay, inspect again.

## Writing the intent down: the modeling layer

The modeling layer is experimental throughout, and it puts the event model in the repository as text a compiler checks, next to the code it describes.

[Event modeling](https://cratis.io/event-modeling/) maps a timeline of screens, commands, events, read models and automations, so the people involved can talk about cause and information flow before anyone writes the implementation. A declared event type is a statement of intent: `AuthorRegistered` in the model says the system is meant to be able to record it. Only the event log says it did.

![A diagram titled One slice on a timeline, labeled Event modeling. In the event model, Reserve screen issues ReserveBook, which produces BookReserved. BookReserved is projected into Availability, which feeds the Catalog screen, and it triggers StockKeeper. In the event log, Recorded BookReserved is an instance of BookReserved.](./model-timeline.png)

[Screenplay](https://cratis.io/screenplay/) writes that model down as a versioned `.play` file. This slice is from [Why Screenplay](https://cratis.io/screenplay/why-screenplay/):

The command produces InvoiceRegistered, mapping invoiceId, invoiceNumber and registeredAt from $context.occurred. It then declares event InvoiceRegistered with invoiceId, invoiceNumber and registeredAt as DateTime.](./code-register-invoice-slice.png)

<summary>Show the code</summary>

```screenplay
slice StateChange RegisterInvoice
  command RegisterInvoice
    invoiceId     InvoiceId
    invoiceNumber InvoiceNumber
    authorize CanManageInvoice
    validate
      invoiceNumber matches "^INV-[0-9]{6}$"  message "Must look like INV-000000"

      invoiceId     = invoiceId

```

The command, its authorization, its validation and the event it produces sit in one file next to the code, in the same history.

Chronicle's [projection declaration language](https://cratis.io/chronicle/projections/projection-declaration-language/) is compiled with the Screenplay compiler, so a projection written as text and a projection in a model share one language.

Around Screenplay:

- Stage, which is experimental, compiles Screenplay, checks the modeled specifications its runner supports, and renders supported Arc and Chronicle application shapes; specification verification and direct runtime execution are partial. The [Stage renderer guide](https://cratis.io/screenplay/stage/guides/build-renderer-target/) shows how a target is built.
- Scene (experimental) separates UI intent from its React renderer.
- [Prologue](https://cratis.io/prologue/), which is experimental, interprets approved metadata signals from selected SQL Server CDC, PostgreSQL logical replication, HTTP and OpenTelemetry sources into a candidate event model for human correction; the captured metadata still needs privacy review.

![A diagram titled One model, many readers, labeled Screenplay. Prologue drafts the .play model, and Screenplay MCP proposes changes to it for review. The .play model is compiled by the Screenplay compiler, feeds Stage, and is read by Synopsis. Chronicle compiles its projection declaration language with the Screenplay compiler. Stage translates to Scene.](./screenplay-hub.png)

There's one rule in Screenplay we care about more than any single feature. Producers and consumers of a model have to declare what they can handle and expose what they can't represent, instead of dropping it silently. A tool that quietly loses part of your model is worse than one that refuses it.

A second model-led change still needs to be proved against a running target. That's where this layer is heading, and we won't put dates on it.

## AI across the layers

One command gives your assistant the Cratis rules and skills, and each layer gives it typed material to check its work against. Each layer also has its own limit on what the assistant may touch.

**Rules and skills.** [`cratis ai install`](https://cratis.io/ai/getting-started/) installs Cratis rules and skills into the assistants you use, for the harnesses, profiles and languages you pick:

```bash
cratis ai install \
  --harnesses claude,codex,copilot,cursor,opencode,pi \
  --profiles cratis/application/csharp,cratis/documentation \
  --languages csharp,typescript
```

That gives an assistant context about how Cratis is meant to be used. It doesn't give it access to anything, and it doesn't make its output correct. The [AI section](https://cratis.io/ai/) of the docs covers what's in the corpus.

**What each layer gives it to read.** At the edge, AuthProxy's configuration is declarative JSON. In the application, the generated TypeScript proxies are typed contracts the frontend compiles against. In the event store, registered event types have schemas an assistant can look up instead of guessing. In the model, the `.play` file is text a compiler checks.

**The model.** Screenplay MCP proposes model changes for a person to review. The [install page](https://cratis.io/screenplay/install-mcp/) starts with `dotnet tool install --global Cratis.Screenplay.Tool`.

**The running system.** [Chronicle MCP](https://cratis.io/chronicle-mcp/) can read a running Chronicle server, which means an assistant connected to it can read event payloads, including personal data. Don't treat it as read-only, and scope what you connect it to. Anything the assistant reads that way is data, not instructions to follow.

**The docs.** [Prompter](https://cratis.io/prompter/) (experimental) answers questions about the Cratis docs in Discord with citations you can follow, or refuses when it can't ground an answer.

### Four kinds of evidence

A proposal, a declared model, a passing specification and a recorded event answer different questions: what was proposed, what the model declares, what a specification checks, and what the running system recorded. A passing specification does not approve a proposal or prove deployed behavior. We think keeping them apart is a useful habit when working with an assistant.

With the author feature: an assistant's diff that stops two authors in tenant Acme registering under the same name is a proposal. The rule written into the event model is a declaration. A spec that registers the same name twice and expects a rejection checks one example. In Chronicle, the rule can be a uniqueness constraint, checked within its event sequence and the Acme namespace when the event is appended. Once the feature runs, the event log in Acme's namespace shows what was actually recorded. The first three are things someone writes; the fourth is what the running system recorded.

![A diagram titled Four kinds of evidence, with four separate boxes and no arrows between them. Proposal: what was proposed? An assistant's diff. Declaration: what does the model declare? The event model. Specification result: what did a spec check? Same name twice. Observation: what was recorded? Acme's event log. A box labeled Docs and MCP results points only to Proposal.](./four-kinds-of-evidence.png)

The [AI assistant walkthrough](https://blog.cratis.io/from-zero-to-first-projection-with-an-ai-assistant/) shows one of these tools used on a real task, including where the assistant was told not to use one.

## When not to use it

The strongest argument against all of this is that you can assemble every layer from well-known parts: an identity provider at the edge, a web framework, a database, OpenAPI generation for the frontend and a test runner. Each part is widely understood, and you avoid tying the application to one vendor's set of products. If your team already has those seams under control, and your data's history carries little business meaning, that's a reasonable choice. Our answer is narrower: evaluate the boundary you need, together with that product's dependencies, rather than adopting the entire ecosystem.

Some systems don't need the event-history part at all. For a small current-state form where nobody needs the story of changes, use a database and keep the extra model, migrations and replay machinery out of the way. Chronicle's docs have a page on [when to use event sourcing](https://cratis.io/chronicle/concepts/when-to-use-event-sourcing/), and Screenplay is the wrong tool for a slice that's mostly custom code.

Keeping facts also comes with a bill. Someone owns the old event schemas, the lag between write and read, the identity that makes side effects safe to repeat, the replay decisions and the matching restore sets. The day 400 section is that bill, itemized.

## Where each piece stands, and what's next

The products above have different release and experimental statuses. Here they are in one place.

Cratis publishes a connected .NET product path in which Arc owns CQRS application contracts, Components provides React components aligned with Arc application patterns, Chronicle supplies an independently usable event-sourced runtime, and Workbench and the Cratis CLI provide bounded Chronicle inspection surfaces; each product retains its own package, release, compatibility, license, support, and independent-use boundary.

Chronicle and its bundled local Workbench are available as MIT-licensed self-hosted software; authorized local use is separate from paid Cratis support, hosted coordination, or managed operational responsibility. For other products, check the license in each repository instead of assuming it.

- **Experimental:** Screenplay, Stage, Scene, Prologue, Narrator and Prompter. Syntax and behavior in these can still change.
- **Source preview, not published to npm:** Arc for TypeScript.

For AuthProxy, Arc for Kotlin/Java, Specifications, Synopsis and Chronicle MCP, we don't assign a maturity label where the product's own documentation states none. The experimental, source-preview and v0.x labels above are the products' own.

Two more things we're building:

We're building Cratis Studio: an experimental, collaborative place where people and AI design, visualize and edit the same event model. It's early, and we'll share more when there is more to show.

We're building Cratis Direct: it turns repository signals into one prioritized queue of bounded AI work, and brings the results back as pull requests for people to review. It is an internal experiment the team uses on its own work.
