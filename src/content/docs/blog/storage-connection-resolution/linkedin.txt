Where does each tenant's data live?

If your platform decides (a server per region, a database per customer, a login that sees one tenant and nothing else), a framework that derives database names and connects with one credential gets in your way.

Chronicle and Arc can now ask instead. The caller says what the connection is for: the storage, the purpose, the tenant. A resolver answers with only the parts it decides. Everything it leaves out stays as configured, and nothing changes until you configure it.

In the post I wire one example three ways:
- a Chronicle kernel that places each namespace with a naming rule, in configuration only
- an Arc app that asks an HTTP endpoint for each tenant's database and login
- a small client with no Arc in it that asks the same endpoint

The contract is a plain JSON request and answer, so the endpoint can be written in anything. Arc is a convenience, not a requirement.

The part worth reading even if you never use it: the example has a tenant the endpoint doesn't know. Chronicle's template places it anyway. The endpoint refuses it. Choosing a tenant is not authorizing it, and the post shows where that line sits.
