Almost every read model starts out innocent. A work item has a title, so you add a `Title`. Then it needs to know whether it's still a backlog entry or has become a pull request, so you add a `Status`. Then pull requests have a URL, and builds have a result, and suddenly you have a record where half the properties are nullable and every query begins with "first, filter on status, *then* you can trust the rest".

Let's face it, that's the shape of the data fighting the shape of the model. A backlog entry and a pull request aren't the same thing with different flags. They're different things an entity is at different times, and they have different properties. I wrote about the declarative side of projections in [*Keep the projection out of the model*](/keep-the-projection-out-of-the-model/). This post is about a feature that works in both styles, and that I like a lot: **variants**.

## TL;DR

- A variant group is a set of read models for the *same* logical entity, where the entity is in **exactly one** of them at a time.
- Each variant has only the properties its stage has. No `Status`, no nullable leftovers.
- When an entity enters one variant, Chronicle removes it from the others. You don't write the removal.
- Only the variant's **entering event** can create it. Any other event it listens to can only update an instance that already exists, so a late or replayed event can't resurrect something that has moved on.
- It works with model-bound attributes and with the fluent builder. The fluent one has no equivalent of `[GlobalFor<T>]`.
- Each variant is its own collection or table, and nothing queries across the group for you.

## One entity, several shapes

The documentation uses a work item that is a backlog entry until a pull request exists for it, and then a pull request. Modeled as one read model, you get the `Status` problem from the intro. With variants, you declare one read model per stage instead.

Two things make that work. First, every variant points at the same *identity type*, which is what ties them into a group. Second, each variant names the event that **enters** it. Here it is with model-bound attributes. As in the last post, the tabs are synced, so pick your language once.

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Projections.ModelBound;

[EventType]
public record IssueCreated(string Title);

[EventType]
public record PullRequestCreated(string PullRequestUrl);

/// <summary>
/// Anchors the logical identity shared by every variant. It does not need to be a
/// read model itself, and it does not need a common CLR base type with any of the variants.
/// </summary>
public class WorkItem;

[VariantOf<WorkItem>]
[EntersOn<IssueCreated>]
public record BacklogItem([property: Key] Guid Id, string Title);

[VariantOf<WorkItem>]
[EntersOn<PullRequestCreated>]
public record PullRequestItem([property: Key] Guid Id, [property: SetFrom<PullRequestCreated>] string PullRequestUrl);
```

`WorkItem` is only an anchor. It doesn't have to be a read model, and it doesn't need a common base type with the variants. Its job is to be the shared type that every variant in the group points at, which is why the docs suggest choosing one that means something on its own, rather than a marker with no purpose beyond grouping.

Now follow an entity through it. When `IssueCreated` is processed, a `BacklogItem` is created, and `Title` maps by convention just like in any other projection. When `PullRequestCreated` is processed for the same entity, a `PullRequestItem` is created **and the `BacklogItem` for that entity is removed**. There's no `RemovedWith` anywhere. The group takes care of it. Variants aren't required to be entered in any particular order, only to be mutually exclusive once entered, so a `PullRequestCreated` for an entity that was never a backlog item still creates a `PullRequestItem`.

A third variant for a later stage, say a closed work item, would be declared the same way, with its own entering event.

Here is what that says in specifications. First, an issue makes a backlog item:

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Testing.ReadModels;
using Cratis.Specifications;
using Xunit;

public class when_an_issue_is_created : Specification
{
    readonly EventSourceId _workItemId = EventSourceId.New();
    readonly ReadModelScenario<BacklogItem> _backlog = new();

    Task Because() => _backlog.Given.ForEventSource(_workItemId).Events(new IssueCreated("Fix the login redirect"));

    [Fact] void should_be_in_the_backlog() => _backlog.Instance!.Title.ShouldEqual("Fix the login redirect");
}
```

Then a pull request for the same work item, with one `ReadModelScenario` per variant fed the same history:

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Testing.ReadModels;
using Cratis.Specifications;
using Xunit;

public class when_a_pull_request_is_created_for_a_backlog_item : Specification
{
    readonly EventSourceId _workItemId = EventSourceId.New();
    readonly ReadModelScenario<BacklogItem> _backlog = new();
    readonly ReadModelScenario<PullRequestItem> _pullRequest = new();

    async Task Because()
    {
        object[] history = [new IssueCreated("Fix the login redirect"), new PullRequestCreated("https://example.com/pull/42")];

        await _backlog.Given.ForEventSource(_workItemId).Events(history);
        await _pullRequest.Given.ForEventSource(_workItemId).Events(history);
    }

    [Fact] void should_no_longer_be_in_the_backlog() => (_backlog.Instance is null).ShouldBeTrue();
    [Fact] void should_be_a_pull_request() => _pullRequest.Instance!.PullRequestUrl.ShouldEqual("https://example.com/pull/42");
}
```

There's a nice property hiding in how this is built. Each variant compiles to an ordinary, independent projection definition, and the [release that introduced variants](https://github.com/Cratis/Chronicle/releases/tag/v19.1.0) made no kernel, wire or storage changes. So there's nothing new to operate. A variant is a projection like any other, and the engine does the exclusion.

## Only the entering event can create a variant

Variants rarely listen to one event. A pull request also wants to know how its build went. You declare that exactly as you would on any projection, with `SetFrom` in the model-bound case. The one difference is what that mapping is allowed to do: it can update a variant that already exists, but it can never create one.

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Projections.ModelBound;

[EventType]
public record PullRequestCreated(string PullRequestUrl);

[EventType]
public record BuildCompleted(string BuildStatus);

public class WorkItem;

/// <summary>
/// BuildStatus is mapped from BuildCompleted - an event that is NOT this
/// variant's entering event, so it is automatically reclassified into an update-only join. It can bring
/// an already-active instance up to date, but it can never create one on its own.
/// </summary>
[VariantOf<WorkItem>]
[EntersOn<PullRequestCreated>]
public record PullRequestItem(
    [property: Key] Guid Id,
    [property: SetFrom<PullRequestCreated>] string PullRequestUrl,
    [property: SetFrom<BuildCompleted>] string BuildStatus);
```

`BuildStatus` is mapped from `BuildCompleted`, which isn't the event named in `EntersOn`. Chronicle reclassifies that mapping into an update-only join on the variant's own key before it ever reaches the projection engine. The entering event stays the only door in.

![A diagram titled Only the entering event creates a variant. Three events on the left, each with an arrow to a result. IssueCreated: BacklogItem created. PullRequestCreated: PullRequestItem created, BacklogItem removed. BuildCompleted: PullRequestItem updated, only if it already exists. A red band reads A late or replayed BuildCompleted cannot bring a variant back.](./only-the-entering-event.png)

The docs explain why this matters, and it's the part of the feature I find most convincing. Without that reclassification, a `BuildCompleted` that arrives out of order, or is replayed, could **resurrect** a `PullRequestItem` for an entity that has since moved on to another variant, or one that was never a pull request at all. That's exactly the bug a status column invites, and here it's structurally impossible. You don't have to reason about event ordering to get the guarantee. Declaring the entering event gives it to you.

You can see that in specifications too. A build for something that never became a pull request creates nothing:

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Testing.ReadModels;
using Cratis.Specifications;
using Xunit;

public class when_a_build_completes_for_something_that_is_not_a_pull_request : Specification
{
    readonly EventSourceId _workItemId = EventSourceId.New();
    readonly ReadModelScenario<PullRequestItem> _pullRequest = new();

    Task Because() => _pullRequest.Given.ForEventSource(_workItemId).Events(new BuildCompleted("passed"));

    [Fact] void should_not_create_a_pull_request() => (_pullRequest.Instance is null).ShouldBeTrue();

```

And when the pull request exists, the build status lands on it:

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Testing.ReadModels;
using Cratis.Specifications;
using Xunit;

public class when_a_build_completes_after_the_pull_request_was_created : Specification
{
    readonly EventSourceId _workItemId = EventSourceId.New();
    readonly ReadModelScenario<PullRequestItem> _pullRequest = new();

    Task Because() => _pullRequest.Given.ForEventSource(_workItemId).Events(
        new PullRequestCreated("https://example.com/pull/42"),
        new BuildCompleted("passed"));

    [Fact] void should_report_the_build_status() => _pullRequest.Instance!.BuildStatus.ShouldEqual("passed");
}
```

So what about a build that finishes *before* the pull request exists? The first spec says it creates nothing, and that holds. What happens once the pull request does arrive is more interesting. `BuildStatus` is mapped through a join, and joins are re-resolved against the last stored event of the joined stream whenever the projection handles one of the read model's own events. So the earlier `BuildCompleted` is picked up the moment `PullRequestCreated` creates the variant:

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Testing.ReadModels;
using Cratis.Specifications;
using Xunit;

public class when_a_build_completes_before_the_pull_request_was_created : Specification
{
    readonly EventSourceId _workItemId = EventSourceId.New();
    readonly ReadModelScenario<PullRequestItem> _pullRequest = new();

    Task Because() => _pullRequest.Given.ForEventSource(_workItemId).Events(
        new BuildCompleted("passed"),
        new PullRequestCreated("https://example.com/pull/42"));

    [Fact] void should_still_create_the_pull_request() => _pullRequest.Instance!.PullRequestUrl.ShouldEqual("https://example.com/pull/42");
    [Fact] void should_pick_up_the_build_status_reported_before_entering() => _pullRequest.Instance!.BuildStatus.ShouldEqual("passed");
}
```

I also appended the same two events to a running Chronicle server, and it gives the same answer. If your build can really finish before the pull request exists, that's still worth a thought about your events, but the projection won't lose the result.

## Sharing a mapping across variants

Some properties every stage wants. A title is the obvious one. Repeating the mapping on each variant gets old, so model-bound projections have `[GlobalFor<TIdentity>]`: declare the mapping once, and it's merged into every variant in the group. The other clients spell this their own way, and the [model-bound variants page](https://cratis.io/chronicle/projections/model-bound/variants/) has all five.

{/* group:shared */}

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Projections.ModelBound;

[EventType]
public record IssueCreated(string Title);

[EventType]
public record PullRequestCreated(string Title, string PullRequestUrl);

[EventType]
public record TitleChanged(string Title);

public class WorkItem;

[VariantOf<WorkItem>]
[EntersOn<IssueCreated>]
public record BacklogItem([property: Key] Guid Id, string Title);

[VariantOf<WorkItem>]
[EntersOn<PullRequestCreated>]
public record PullRequestItem([property: Key] Guid Id, string Title, string PullRequestUrl);

[GlobalFor<WorkItem>]
public record SharedHandlers([property: SetFrom<TitleChanged>] string Title);
```

This block is its own small example, with a fresh set of events. `SharedHandlers` is not a read model and no variant inherits from it. It only carries the mapping, and `TitleChanged` now updates the title on whichever variant the work item is in:

```csharp
using Cratis.Chronicle.Events;
using Cratis.Chronicle.Keys;
using Cratis.Chronicle.Testing.ReadModels;
using Cratis.Specifications;
using Xunit;

public class when_the_title_changes_after_the_pull_request_was_created : Specification
{
    readonly EventSourceId _workItemId = EventSourceId.New();
    readonly ReadModelScenario<PullRequestItem> _pullRequest = new();

    Task Because() => _pullRequest.Given.ForEventSource(_workItemId).Events(
        new IssueCreated("Fix login"),
        new PullRequestCreated("Fix login", "https://example.com/pull/42"),
        new TitleChanged("Fix the login redirect"));

    [Fact] void should_have_the_new_title() => _pullRequest.Instance!.Title.ShouldEqual("Fix the login redirect");
}
```

Like any other non-entering mapping, a shared one can only update an active variant, so it's safe to share across stages that begin at different times. And every variant must have the member a shared mapping targets. A variant without it is a declaration error, caught when the projection is discovered, not an unpredictable surprise when a shared event finally shows up.

## The same thing, fluent

Everything above is also available in the declarative style, and this is where the two styles from the last post line up one to one.

![A diagram titled Same group, two spellings. Model-bound column: VariantOf of T, EntersOn of E, SetFrom of E, GlobalFor of T. Fluent column: .VariantOf of T with a key lambda, .EntersOn of E, .From of E, and Repeat .From of E on each variant for the one that has no equivalent. A band reads Both build the same mutually exclusive group.](./two-spellings.png)

The read models are plain records, the projections say which group and which entering event, and the identity type is declared exactly as before.

```csharp
public record IssueCreated(string Title);

public record PullRequestCreated(string PullRequestUrl);

/// Deliberately not a read model itself, and does not need a common CLR base type with either variant.
/// </summary>

public record BacklogItem(Guid Id, string Title);

public record PullRequestItem(Guid Id, string PullRequestUrl);

public class BacklogItemProjection : IProjectionFor<BacklogItem>
{

        .VariantOf<WorkItem>(_ => _.Id)
        .EntersOn<IssueCreated>();

{
    public void Define(IProjectionBuilderFor<PullRequestItem> builder) => builder
        .VariantOf<WorkItem>(_ => _.Id)
```

`From<BuildCompleted>()` looks like any other subscription. Because it isn't the entering event, the builder turns it into an update-only join keyed on the same property `VariantOf` named, before the definition reaches the engine. Same guarantee, spelled differently.

The one real difference is sharing. Fluent projections have no equivalent of `[GlobalFor<T>]`. Each projection is its own class with its own definition, so a mapping every variant needs is a `.From<TEvent>()` on each builder. The docs' own advice is that if you end up repeating one often enough for it to hurt, that repetition is a reason to use model-bound variants for that group.

The first specification in this post, with the same history and the same assertions against `FluentBacklogItem` and `FluentPullRequestItem`, passes for the fluent version too. A `ReadModelScenario` discovers the other variants of the group, model-bound or fluent, so entering one variant removes the entity from the others there as it does on a server.

## What it costs

Be honest with yourself about the trade, because there is one.

- **Each variant is its own collection.** There's no built-in query that spans the group. If a caller needs "this entity, whichever stage it's in", it asks each variant explicitly. That's by design, and it's also something you have to build.
- **The shapes have to genuinely differ.** If every stage shares nearly all its properties and differs by a flag or two, a single read model with a `Status` is still the right answer. The docs say so too.
- **It's a projection feature.** Variants are declared on model-bound and fluent projections. A reducer builds the state of one read model, so it's not where this lives. If you're deciding between a projection and a reducer, the previous post and [*From event to read model*](/from-event-to-read-model/#when-attributes-cant-say-it-reducers) cover the difference.

And what do you get for it? The fastest thing that can possibly work, as I like to put it. A query for the backlog reads the backlog. There's no `Status` to filter on, so there's none to index just to keep that lookup quick, and the rows you don't want aren't in the way. That's the design bet. I haven't benchmarked it for this post, so don't take it as a number. Take it as the reason the shape exists.

## Wrapping up

The next time you reach for a `Status` column, ask whether you're modeling a flag or a different thing. If it's a different thing, give it its own read model, name the event that makes an entity become it, and let Chronicle do the moving. That's a few attributes, or a few builder calls, and a status filter you never write.

The full reference is in the docs, for both [model-bound variants](https://cratis.io/chronicle/projections/model-bound/variants/) and [fluent variants](https://cratis.io/chronicle/projections/declarative/variants/), and the [guide to choosing a read-model style](https://cratis.io/chronicle/projections/choosing-a-read-model-style/) is a good companion if you're still deciding between the ways to build one. How a read model gets queried afterwards, and how a live list learns about changes, is in [*From event to read model*](/from-event-to-read-model/).
